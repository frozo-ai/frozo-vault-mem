## 1. Context & purpose

Phase 1+2+3 shipped a working local-first memory layer: MCP server with hybrid search, Python keeper daemon with triage/link/decay/archive ops. The vault stays coherent through autonomous mechanical work — but it can't yet *notice* that two memories disagree, and it can't yet *summarize* what's in a project.

Phase 5 adds two LLM-driven keeper ops that close those gaps:

1. **Contradiction detection** — for each memory newly promoted to canonical, the keeper finds its semantic neighbors via Lance and runs them through a Haiku pre-filter + Sonnet judge. Real contradictions surface as proposals in `_system/proposals.jsonl` for human review via a new `vault-mem-keeper review` CLI.
2. **Summarization** — periodic per-project rollups (daily/weekly/monthly) generated by Sonnet from recent memories, written as `summary` memories with a `covers: [memory_ids]` provenance field.

Done-when (PRD §8): *"Daemon surfaces a real contradiction unprompted that I'd have missed."*

This phase introduces the project's first external API dependency (Anthropic's `anthropic` Python SDK) plus a soft monthly cost cap with audit logging. No code paths in the MCP server change. All LLM work happens in the keeper.

## 2. Scope

**In scope:**
- New `packages/keeper/src/vault_mem_keeper/llm/` package: client, prompts, budget tracker.
- New keeper ops: `ops/contradict.py`, `ops/summarize.py`.
- New `proposals.py` module + `_system/proposals.jsonl` file format.
- New CLI: `vault-mem-keeper review` (interactive walker for proposals).
- New audit op types: `contradict_scan`, `summarize`, `budget_exceeded`, `proposal_applied`, `proposal_rejected`.
- New config sections: `keeper.contradict`, `keeper.summarize`, `keeper.budget`.
- New state file: `_system/state.json` (last-run timestamps for incremental work).
- New gitignored vault file: `_system/budget.jsonl` (per-call cost tracking).
- TS-side `AuditEntry` union widening for the new op shapes.

**Out of scope** (deferred to Phase 4, Phase 6, or never):
- Telegram approval gate (Phase 4 — adds a transport for the same proposal queue, doesn't replace it).
- Auto-apply destructive ops without human review.
- Pluggable LLM providers (Anthropic-only by design).
- Streaming Sonnet responses to the CLI walker.
- Cost dashboards beyond the raw JSONL log.
- Cross-vault contradiction detection.
- Real-time contradiction detection in the MCP server's `memory_write` path (kept batch-only for server speed).
- Auto-tuning decay rates from contradiction signal.
- Sonnet inference of `tags` / `project` for un-tagged memories (Phase 6 polish).
- Merge proposals that *create* a third memory from two (gated behind `--allow-merge` flag; default behavior is open both files in `$EDITOR` for human-driven merge).

## 3. Architecture overview

### 3.1 Where Phase 5 lives

In the Python keeper. Two new ops added to the daemon's run order, plus one new CLI command. The TS MCP server is unchanged.

**Updated keeper run order:**

```
triage → link → decay → archive → contradict → summarize
```

Contradict and summarize fire after the existing four because they need post-triage canonical memories and post-link fresh embeddings. Summarize last so it sees same-run contradictions/archives.

Soft cap, configurable. Default `$5.00/month`. ## 4. Operations

### 4.1 Contradiction detection (`ops/contradict.py`)

**Trigger:** at the end of each keeper run, identify memories currently in `memory/` whose `updated` field is newer than `state.last_contradict_at`. This captures both freshly-promoted memories AND memories whose content was edited since the last pass — both cases warrant a fresh contradiction check. For each such memory, look for conflicts among its Lance neighbors.

**Two-pass algorithm:**

```python
def run_contradict(paths, cfg, schemas, audit, llm_client, *, dry_run, run_id) -> ContradictReport:
    if not cfg.contradict.enabled or not llm_client.has_key():
        return ContradictReport(skipped=True, reason="disabled or missing API key")

    state = read_state(paths.state_file)
    threshold = state.get("last_contradict_at", "1970-01-01T00:00:00Z")

    # Memories promoted to canonical since last contradict pass
    fts = FtsReader(paths.index_file)
    new_canonical = [m for m in fts.list({"location": "memory", "status": "active"})
                     if m["updated"] > threshold
                     and m["type"] in cfg.contradict.types_to_scan]

    lance = LanceReader(paths.lance_dir)
    proposals = ProposalWriter(paths.proposals_file)

    pairs_judged = 0
    proposals_written = 0
    total_cost = 0.0

    for M in new_canonical:
        m_lance = lance.get_by_id(M["id"])
        if not m_lance: continue
        neighbors = lance.search(m_lance["vector"],
                                  filter_={"status": "active", "location": "memory",
                                           "type": M["type"]},
                                  limit=cfg.contradict.top_k + 1)
        for N in neighbors:
            if N["id"] == M["id"]: continue
            if proposals.already_judged(M["id"], N["id"], M["updated"]):
                continue

            # Pre-filter: same topic?
            same_topic, cost1 = llm_client.haiku(
                CONTRADICT_PREFILTER.format(M=M, N=N),
                budget=cfg.budget,
            )
            total_cost += cost1
            if not same_topic.is_yes():
                continue
            pairs_judged += 1

            # Judge: actual contradiction?
            judgment, cost2 = llm_client.sonnet(
                CONTRADICT_JUDGE.format(M=M, N=N),
                budget=cfg.budget,
                response_format="json",
            )
            total_cost += cost2

            if not judgment.has_contradiction:
                continue
            if judgment.severity not in (cfg.contradict.min_severity, "high"):
                continue

            if not dry_run:
                proposals.append({
                    "v": 1,
                    "id": new_proposal_id(),
                    "status": "pending",
                    "created_at": now_iso(),
                    "kind": "contradict",
                    "source_id": M["id"],
                    "target_id": N["id"],
                    "severity": judgment.severity,
                    "reasoning": judgment.reasoning,
                    "suggested_action": judgment.suggested_action,
                    "model": "claude-sonnet-4-7",
                    "cost_usd": cost1 + cost2,
                    "run_id": run_id,
                    "source_updated": M["updated"],
                    "target_updated": N["updated"],
                })
                proposals_written += 1

    state["last_contradict_at"] = now_iso()
    if not dry_run:
        write_state(paths.state_file, state)
        audit.write({
            "op": "contradict_scan",
            "agent": "keeper",
            "session": run_id,
            "memories_scanned": len(new_canonical),
            "pairs_judged": pairs_judged,
            "proposals_written": proposals_written,
            "cost_usd": total_cost,
        })
    return ContradictReport(...)
```

**Cost shape per run** (50 writes/day, ~25 promoted/day, 5 neighbors each → 125 Haiku calls):

- Haiku pre-filter: 125 × $0.0001 = $0.013/day
- Sonnet judge (assume 15% Haiku-positive): ~19 × $0.003 = $0.057/day
- Total contradiction: ~$2/month at user volume

**Idempotency (with order-normalization):** `proposals.already_judged(M.id, N.id, M.updated, N.updated)` returns true if the file contains an entry covering the same pair. The pair lookup must normalize order: a proposal stored as `(source=A, target=B)` and a query for `(source=B, target=A)` count as the same pair. The dedup key is therefore `(sorted(A.id, B.id), max(A.updated_in_proposal, B.updated_in_proposal))`. A pair is re-evaluated only when *either* memory's `updated` field has advanced since the proposal was stored — capturing both cases of "M was edited" and "N was edited."

### 4.2 Summarization (`ops/summarize.py`)

**Trigger:** end of each keeper run. For each project, for each period (daily/weekly/monthly), check whether a fresh summary is needed.

**Regeneration criteria:**

| Period | Stale after | New-memory threshold |
|---|---|---|
| `daily` | 24h since last daily summary for project | ≥5 new memories of any type |
| `weekly` | 7d since last weekly | ≥20 new memories |
| `monthly` | 30d since last monthly | ≥80 new memories |

Both clauses are AND'd. Daily summaries don't generate just because a day passed; they need *both* time AND volume. Avoids spamming summaries for inactive projects.

**Algorithm per `(project, period)` refresh:**

```python
def regenerate_summary(paths, cfg, schemas, audit, llm_client, project, period, *, run_id) -> bool:
    fts = FtsReader(paths.index_file)
    cutoff = now() - timedelta(days={daily:1, weekly:7, monthly:30}[period])
    candidates = fts.list({"project": project, "status": "active", "location": "memory"})
    candidates = [c for c in candidates if c["updated"] >= cutoff.isoformat()]
    if len(candidates) == 0: return False

    # Order by bucket priority then recency desc
    bucket_order = ["decision", "learning", "observation", "summary",
                    "todo", "entity", "question"]
    ordered = sorted(candidates, key=lambda c: (bucket_order.index(c["type"]),
                                                 -isoparse(c["updated"]).timestamp()))
    ordered = ordered[:cfg.summarize.max_input_memories]

    prompt = SUMMARY_TEMPLATES[period].format(
        project=project, memories=ordered,
        max_tokens=cfg.summarize.max_input_tokens,
    )
    body, cost = llm_client.sonnet(prompt, budget=cfg.budget)

    summary_id = generate_id()
    summary_fm = {
        "id": summary_id,
        "type": "summary",
        "title": f"{period.capitalize()} summary for {project} — {date.today().isoformat()}",
        "agent": "keeper",
        "session": run_id,
        "created": now_iso(),
        "updated": now_iso(),
        "confidence": 1.0,
        "tags": [project, period, "auto-generated"],
        "project": project,
        "period": period,
        "covers": [c["id"] for c in ordered],
        "ttl_days": None,
        "status": "active",
        "human_reviewed": False,
        "human_approved": None,
        "schema_version": "0.1",
    }
    target = paths.memory_file("summary", summary_id, "memory")
    atomic_write(target, serialize_memory(summary_fm, body))

    audit.write({
        "op": "summarize",
        "agent": "keeper",
        "session": run_id,
        "project": project,
        "period": period,
        "memory_id": summary_id,
        "covers_count": len(ordered),
        "cost_usd": cost,
    })
    return True
```

**Supersession of stale summaries:** prior summaries for the same `(project, period)` are NOT auto-archived. They keep `status: "active"` and stay searchable. Decision: humans/agents may want to see how a project's narrative evolved week-over-week. The decay op archives them naturally if/when they cross the floor (currently `null` decay rate for summaries → permanent).

If you find this clutters Obsidian's graph, set `keeper.summarize.archive_predecessors: true` to opt in.

**Cost:** ~$0.005 per summary (Sonnet, ~6k input + ~1k output). At 3 active projects × ~5 summaries/week each = ~$0.30/month. Negligible.

### 4.3 Cost tracking (`llm/budget.py`)

**Per-call accounting:** every Anthropic SDK call goes through `llm.client.haiku(...)` or `llm.client.sonnet(...)`. The wrapper:

1. Records call start time, model, prompt token count.
2. Makes the call (with backoff on 429/500, max 3 retries).
3. Reads `usage.input_tokens` + `usage.output_tokens` from the response.
4. Computes USD cost from a hardcoded per-model price table.
5. Appends one line to `_system/budget.jsonl`:
   ```json
   {"ts":"2026-05-01T03:00:00.123Z","v":1,"model":"claude-haiku-4-5","input_tokens":420,"output_tokens":12,"cost_usd":0.000094,"op":"contradict_prefilter","run_id":"01KQ..."}
   ```
6. Returns `(response, cost_usd)` to the caller.

**Soft cap enforcement:** before each call, `llm.budget.month_to_date()` reads `budget.jsonl`, sums `cost_usd` for the current calendar month. If it's ≥ `keeper.budget.monthly_usd_cap`:

- Writes a single audit line per run: `{op: "budget_exceeded", monthly_total_usd: …, cap_usd: …}`
- Short-circuits all subsequent LLM calls in the run (returns sentinel `BudgetExceeded` response).
- The op (`contradict` or `summarize`) gracefully degrades — for contradict, it stops scanning new pairs; for summarize, it skips the regeneration and the prior summary stays canonical.

**Default cap: $5.00/month.** Configurable in `_system/config.yaml`.

### 4.4 Belief decay tuning

PRD §8 lists this as a Phase 5 deliverable. In practice, it's a **review task** based on real-world behavior:

After Phase 5 has been running for ~30 days:

1. Look at audit log for `op: "decay"` entries — count memories archived to date by reason.
2. Look at proposals.jsonl for contradicted memories — were they ones we should have decayed sooner?
3. Adjust `keeper.decay.rates.*` defaults if archive rate seems off.

Phase 5 ships with the existing defaults (observation: 30d, learning: 60d). The "tuning" is a calibration task, not a feature, and is covered by changing config.yaml after observed behavior.

## 5. Proposal queue + review CLI

### 5.1 `_system/proposals.jsonl` format

Append-only JSONL, one proposal per line. Status field is mutated in place via JSONL rewriting (read all, mutate target line, atomic temp+rename).

```json
{
  "v": 1,
  "id": "P-2026-05-01_a8f3c0",
  "status": "pending",
  "created_at": "2026-05-01T03:00:00.123Z",
  "kind": "contradict",
  "source_id": "mem_2026-04-15_a8f3c0",
  "target_id": "mem_2026-04-29_b1e9aa",
  "severity": "high",
  "reasoning": "...",
  "suggested_action": "supersede_M_with_N",
  "model": "claude-sonnet-4-7",
  "cost_usd": 0.0034,
  "run_id": "01KQ...",
  "source_updated": "2026-04-15T14:32:00.000Z",
  "target_updated": "2026-04-29T19:48:12.000Z"
}
```

**Lifecycle:** `"pending"` → user reviews → `"accepted"` or `"rejected"` → CLI applies → `"applied"`. A "skipped" proposal stays `pending`. A "rejected" proposal stays in the file with that status; the contradict op skips re-judging the same `(source_id, target_id, source_updated)` triple.

### 5.2 `vault-mem-keeper review` interactive walker

```
3 pending proposals.
Budget this month: $1.27 / $5.00 cap (25%).

[1/3] P-2026-05-01_a8f3c0  contradict  severity=high
─────────────────────────────────────────────────────────
  Source:  mem_2026-04-15_a8f3c0
           "Use Supabase for myapp auth"
           confidence: 0.85  project: myapp  type: decision
           updated: 2026-04-15T14:32:00Z

  Target:  mem_2026-04-29_b1e9aa
           "Migrate myapp to Auth0"
           confidence: 0.7   project: myapp  type: decision
           updated: 2026-04-29T19:48:12Z

  Sonnet's reasoning:
    The April 15 decision specifies Supabase for auth; the April 29
    decision proposes Auth0 for the same project (myapp). The newer
    memory does not populate `supersedes:` so this is likely an
    undeclared reversal rather than scoped to a different layer.

  Suggested action: supersede_M_with_N
    → Mark mem_2026-04-15_a8f3c0 status=superseded; move to archive/
    → Set mem_2026-04-29_b1e9aa.supersedes = ["mem_2026-04-15_a8f3c0"]

  Cost: $0.0034 (model: claude-sonnet-4-7)

  [a]ccept   [r]eject   [s]kip   [v]iew (open both files in $EDITOR)
  [n]otes (add a comment to the proposal record)   [q]uit
> a

✓ Applied. mem_2026-04-15_a8f3c0 archived; mem_2026-04-29_b1e9aa.supersedes updated.
  Audit logged.
```

**Apply semantics by `suggested_action`:**

| Suggested | What "accept" does |
|---|---|
| `supersede_M_with_N` | Set M.status=`superseded`; move M to `archive/`; set N.supersedes += [M.id]. Atomic temp+rename for both file rewrites; rename for archive. |
| `supersede_N_with_M` | Symmetric. |
| `merge` | v0.1 default: prompt "merge requires manual editing — open both in $EDITOR? [y/N]". User writes a new merged memory by hand. Proposal marked `applied` if a new file is saved with `supersedes: [M.id, N.id]`. With `--allow-merge` flag: ask Sonnet to draft a merged body; user edits in `$EDITOR`; save creates the new memory and supersedes both predecessors. |
| `both_active_different_facets` | Marks the proposal `rejected` (Sonnet was wrong about the contradiction). |
| `none` | Same as above. |

**Filter flags:** `--filter`, `--severity`, `--project` narrow the queue. Reject (`r`), skip (`s`), and view (`v`) are read-only.

## 9. Error handling

- **Missing API key** → `contradict` and `summarize` ops set `skipped=true, reason="missing ANTHROPIC_API_KEY"`. Keeper run still completes; other ops unaffected.
- **API 429 / 500 transient** → SDK retry (3x with exponential backoff). Final failure: log `WARN`, increment op `errors`, continue.
- **Sonnet returns malformed JSON** for the JUDGE prompt → log `WARN`, skip the pair (don't write a malformed proposal), increment op `errors`.
- **Budget exceeded** → mid-run short-circuit (see §4.3). Subsequent calls in the run return `BudgetExceeded` sentinel.
- **proposal apply fails** mid-application (e.g., file system error during M's archive move) → CLI writes `op: "proposal_apply_failed"` to audit log with the partial state; user can manually clean up. Idempotent re-apply attempts are blocked by the proposal's `status: "applied"`-check.

## 10. Testing strategy

### 10.1 Unit (Python)

- `llm/client.py` — mocked Anthropic via `monkeypatch`. Asserts: cost calculation correct for known token counts, retries on 429/500, raises after 3 failed retries, parses `usage.input_tokens` + `usage.output_tokens` correctly.
- `llm/budget.py` — `month_to_date()` sums correctly; soft cap detection; jsonl appender atomic.
- `llm/prompts.py` — pure templates; format with various inputs and assert exact prompt text (matters for regression).
- `proposals.py` — JSONL append + targeted status mutation via temp+rename; idempotent dedup of already-judged pairs.
- `cli/review.py` — interactive walker tested with monkeypatched stdin (`input()` substitution); each action path exercised.
- `state.py` — read/write JSON with schema, missing-file fallback to defaults.

### 10.2 Integration (against tmpVault, with mocked Anthropic client)

- `ops/contradict` — seed vault with 3 memories where #1 contradicts #2 (deterministic mock embedder makes them similar; mocked Sonnet returns `has_contradiction: true, severity: high`). Run op. Assert proposal written with correct source/target.
- `ops/summarize` — seed vault with 6 decisions for project=demo, mocked Sonnet returns canned markdown. Run op. Assert one summary memory written to `memory/summaries/` with `period=daily, covers=[6 ids]`.
- Budget enforcement — set cap to $0.001, run op, assert audit line `budget_exceeded` appears and subsequent calls short-circuit.
- Idempotency — run contradict twice in a row with no memory edits in between; second run produces zero new proposals.
- Re-evaluation on edit — write a contradicting memory, accept the proposal, edit one of them, run contradict again; assert a fresh proposal is generated for the new edit.

### 10.3 End-to-end (skipped on CI; runnable locally with real key)

One pytest test gated by `if not os.environ.get("ANTHROPIC_API_KEY"): pytest.skip(...)`. Seeds a known contradiction, runs the keeper, verifies a real Sonnet response produces a sensible proposal. Expensive (~$0.01/run), opt-in.

### 10.4 Mock fixture

`@anthropic_mock` decorator in `tests/conftest.py`. Returns canned responses for known prompts so unit/integration tests are deterministic and offline.

### 10.5 What's deliberately not tested

- Exact Sonnet output text (mocked).
- Network-flake simulation beyond 429/500 retry path.
- The cost figures themselves (only that they're recorded; absolute values are external to the project).

## Appendix B — Cost ceiling rationale

## Appendix C — Why pairwise (not cluster-based) judgments

Sonnet sees memory pairs, not clusters. Cluster-based judgment ("here are 4 memories about auth, which one is the odd one out?") would be more economical per cluster and produce richer reasoning. Pairwise was chosen because:

1. **Proposals stay clean.** Each is a single yes/no decision. Cluster-based proposals would need a third "which member of the cluster is the contradictor?" step.
2. **Idempotency is simpler** with `(source_id, target_id, source_updated)` tuples than with cluster membership.
3. **At vault sizes <1000 memories**, the cost difference is in the noise (~$2/month vs ~$1/month).

If Phase 6 polish reveals cluster-based judgments work better in practice, this is a contained refactor in `ops/contradict.py` — no API changes, no schema changes.
